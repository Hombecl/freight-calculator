# Spec 04 implementation report

Implemented `/consolidation`, `/zh/consolidation`, and `/api/consolidate`. No commit, push, deployment, dependency addition, secret access, or prerender-script changes.

## Files and requirements

- `src/lib/consolidation.ts`: pure async `consolidate(input: unknown)`, exported request/result types, example and limits. Validates objects, unique PO IDs and per-PO SKUs, dimensions, quantities, weights, dates, units, container presets/counts/rates, LCL settings, rules and packing budget. Enforces 30 POs, 60 item types and 3,000 total requested cartons before window filtering.
- Normalizes inputs to cm/kg. Response container dimensions carry cm/in and weights carry kg/lb; boxes and zone geometry retain the existing cm/kg format. SHA-256 input and candidate hashes use `crypto.subtle`. Stable lexical tie-breakers, no randomness, no input mutation.
- Filters ready dates inclusively, returning explicit before-window, after-window and missing-date reasons. Eligible cargo is sorted by priority, ready date, decreasing PO volume and stable PO ID.
- Enumerates allowed container-count combinations, retains at most 12 mixes in the specified 55–85% volume band, and orders by quoted cost when all allowed presets have rates, otherwise container count. Every nonempty packing trial and whole-PO lookahead consumes the global budget (default 40, maximum 120).
- Greedy assignment uses `packWithConstraints`, PO groups, optional unload zones, supplier caps, whole-PO trials and bounded lookahead before splitting an oversized PO into smaller vessels. Earlier-priority placements cannot be displaced by later trials. Door-incompatible cartons remain unplaced. Fragile means zero permitted weight on top; upright, support, payload and crush limits remain enforced.
- Every plan accounts for eligible cartons in actual containers or explicit PO/SKU remainder. Plans include `containerChecks` with preset door/tare, the four required plan checks, candidate hashes, LCL minimum-volume economics and nullable total/per-carton costs. Returns up to three distinct ranked plans, search counters, outcome, shared check semantics and notes.
- `functions/api/consolidate.ts`: GET example/contract/limits/docs, POST, OPTIONS, keyed anonymous quotas of 5/minute and 50/day, streamed 64 KiB body cap, CORS including key/bearer headers, 200/400/413/415 responses, validation field paths, success tier and invalid-key warning. Shared quota rejection returns 429.
- `src/pages/ConsolidationPage.tsx`: bilingual PO table, add/remove PO, supplier/date/priority, editable carton dimensions/quantities/weights/stack constraints, paste and CSV/Excel uploads through `importCartons`, units conversion, inclusive window, optional container quotes/counts, LCL rate/minimum, rules and budget. Import warnings block replacement and are displayed rather than silently accepting a shortened import.
- Plan cards display container/PO membership, carton count, utilisation, both weight units, check badges/assumptions, remainder by PO/SKU, LCL estimate and cost per carton when rates are complete. Downloads include complete plan JSON, per-container packing CSV using `exportPlan.ts`, the exact completed API request and curl script.
- `src/components/InteractiveLoadPlanner.tsx`: added opt-in `readOnly` and `placedCountTestId` props. Read-only mode disables pointer cargo movement, keyboard mutations and edit controls, preserving camera orbit/zoom. Consolidation uses PO colours and a legend; `container-placed-count` comes from the viewer's box collection. Existing consumers retain editable behavior by default.
- Page includes Helmet metadata, heuristic/booking/economics notes and `tool_consolidation` / `consolidation_run` outcome tracking.

## Edge-case decisions and known limits

- The spec's strict volume band can contain no mix for a small shipment, insufficient allowed capacity, or indivisible container sizes. In this case, an explicit, response- and UI-labelled extension screens up to 12 closest-volume allowed combinations; it does not pretend they satisfy the band. With all counts zero, a remainder-only plan accounts for every eligible carton. This is the deliberate extension to the literal enumeration rule.
- Optional `maxCount` defaults to 12 per preset and accepts 0–120. Priority defaults to 2 and upright defaults to true, matching the quoting safety pattern. Missing supplier names count as separate suppliers per PO. These defaults are documented rather than inferred as known supplier identity.
- Whole-PO placement remains a bounded heuristic preference, not a guarantee that every feasible partition will be discovered. A budget can end during a mix; all remaining cargo is returned explicitly. Unload zones inherit the existing engine's proportional zone-length and payload allocation, which can be conservative.
- Complete FCL plans rank ahead of plans with remainder; comparable supplied total costs then rank ascending, followed by fewer used containers and greater average utilisation. `found` means at least one actual container load was found (or there was no eligible cargo), not that every carton shipped. `ALL_CARGO_PLACED` fails for FCL remainder even when LCL economics are available.
- Currency is labelled `user-supplied`: the specified request has no currency-code field. All entered rates must use one currency; missing required rates yield null total cost. “Per unit” means per eligible carton. No third-party rates, tariffs, fees or fines were invented.
- LCL is only a volume/cost fallback, not a geometric LCL load or booking. Origin/destination charges and cut-offs have no separate model; quote rates may include charges. Existing screening semantics remain explicit, including `not_evaluated` axle, VGM and zone checks.
- Reuses the existing Three.js/CDN renderer and its WebGL fallback. No new renderer was introduced.

No requested feature was skipped. Full-site browser regression execution was outside the required typecheck/unit-test gate; the new browser scenario was executed separately as described above.
